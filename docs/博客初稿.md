**计划与实际差异分析**

1. **表达式解析超时约 40 分钟。** 原计划用调度场算法把中缀表达式转后缀再求值，写到一元负号时发现 `3*-2` 会被当成二元减号处理。改成递归下降文法、把一元正负号单独设为一层规则后彻底解决。
2. **部署环节超出预期。** Render 首次构建失败，日志显示找不到 `pydantic-core` 预编译轮子。原因是平台默认使用 Python 3.14 而该版本轮子不全，添加环境变量 `PYTHON_VERSION=3.12.0` 后通过。
3. **冷启动问题额外消耗时间。** 前端默认 15 秒超时，在免费实例冷启动时持续报「网络错误」，误以为又是 CORS 问题排查较久，最后定位是冷启动耗时超过超时阈值。

### 3.3 小数精度

![图6 小数精度](screenshots/06-小数精度.png)

**图 6 小数精度验证。** `0.1+0.2` 返回精确的 `0.3`，而不是二进制浮点常见的 `0.30000000000000004`。这是因为后端采用 Python 的 `Decimal` 做十进制运算，而非默认的 `float`。图中同时打开 Windows 计算器作对比。

### 3.4 复合表达式（功能二）

![图7 运算优先级](screenshots/07-运算优先级.png)

**图 7 运算优先级验证。** `1+2*3` 返回 `7` 而非 `9`，说明后端正确实现了「乘除优先于加减」。

![图8 括号与嵌套](screenshots/08-括号.png)

**图 8 括号与嵌套表达式。** `(1+2)*3` 返回 `9`，`((2+3)*(4-1))/5` 返回 `3`，验证了括号改变运算优先级以及多层嵌套括号的解析能力。

![图9 一元正负号](screenshots/09-一元正负号.png)

**图 9 一元正负号处理。** `-5+8` 返回 `3`（首个操作数为负数），`3*-2` 返回 `-6`（运算符后紧跟负号）。这两种情况要求解析器能区分二元减号与一元负号，本项目在文法中单独设置了一元运算符层级。

![图11 除零处理](screenshots/11-除零处理.png)

**图 11 除零处理。** `1/0` 被后端显式拦截，返回错误码 `DIVISION_BY_ZERO` 与提示「除数不能为零」。

**非功能需求**

| 类别 | 要求 | 实现方式 |
| --- | --- | --- |
| 安全性 | 禁止 `eval`/`exec` 执行用户输入 | 手写词法分析 + 递归下降文法 |
| 安全性 | 防止 SQL 注入 | 全部使用参数化查询 |
| 安全性 | 防止 XSS | 前端用 `textContent` 而非 `innerHTML` 渲染用户输入 |
| 安全性 | 防止资源耗尽 | 表达式长度上限 200 字符、结果上限 `1e100` |
| 正确性 | 小数运算无浮点误差 | 使用 `Decimal` 十进制运算 |
| 可维护性 | 分层清晰、职责单一 | 后端四层架构、前端四层模块 |
| 可测试性 | 核心逻辑可独立测试 | 表达式引擎不依赖 Web 框架 |
| 可用性 | 助教无需复杂配置即可运行 | 前端零构建、后端 SQLite 零配置 |
| 兼容性 | 不依赖特定本地环境 | 纯标准库 + 少量通用依赖 |
| 可访问性 | 键盘可完整操作 | 语义化标签、ARIA 属性、`:focus-visible` |

**关键约束（来自作业要求）**：核心计算必须由后端完成；禁止 `eval`/`exec`；历史必须持久化到后端数据库；前后端必须分离；代码放在两个独立仓库。

```
└── 后端

    └── 计算服务、异常处理、数据库访问
```

**一次计算的完整数据流**

```
①用户点击「=」→ 前端读取输入 "12+8"
②POST /api/calculate  {"expression": "12+8"}
③接口层：Pydantic 校验结构 + 长度与字符白名单校验
④业务层：词法分析 → 递归下降语法分析 → Decimal 求值
⑤数据访问层：INSERT INTO calculation_history
⑥返回 201 {"success":true,"result":"20","record":{...}}
⑦前端渲染 result，并重新查询历史列表
```

前端在整个流程中只参与 ① 和 ⑦（取输入、显示输出），**不参与任何数值计算**。

### 4.3 前端设计

**技术选型：原生 HTML5 + CSS3 + JavaScript，不使用框架与构建工具。** 理由：作业原文明确说明「技术复杂度本身只占一定分数」，主要目标是达成功能并理解前后端分离；零构建意味着助教 clone 后只需一个静态服务器即可运行，不会因 npm 环境问题卡住验收。

**模块划分（依赖方向严格单向）**

| 文件 | 职责 | 不做什么 |
| --- | --- | --- |
| `config.js` | 存放可调参数（后端地址、超时、分页大小） | 无逻辑 |
| `api.js` | 所有 HTTP 通信、错误归一化 | **不含任何 DOM 操作** |
| `ui.js` | 把数据渲染成界面 | **不发网络请求** |
| `app.js` | 串联用户操作与接口调用 | **不含 fetch，不含计算** |

**界面布局**：左右两栏 Grid，窄屏（<980px）降级为单列。左侧为模式标签、显示屏、键盘；右侧为搜索框、统计卡片、历史列表、分页。

**交互设计要点**

| 要点 | 实现 | 目的 |
| --- | --- | --- |
| 计算中状态 | 按钮置灰 + 显示「计算中…」 | 防止重复提交 |
| 双通道错误提示 | 结果区红字（详细）+ 顶部浮动条（醒目） | 用户不会错过错误 |
| 记录分类色条 | 左边缘 3px：扩展功能绿色、收藏黄色 | 一眼区分记录类型 |
| 智能括号 | 统计左右括号数量，自动补缺的一侧 | 减少输入负担 |
| 点击历史复用 | 点击记录把表达式填回输入框 | 便于连续计算 |
| 主题切换 | CSS 变量 + `data-theme` + localStorage | 无闪烁，记住偏好 |
| 无障碍 | 语义化标签、`aria-label`、`aria-live`、`:focus-visible` | 键盘可完整操作 |

### 4.4 后端设计

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| Web 框架 | FastAPI 0.115 | 自动生成 OpenAPI 文档，助教可直接在浏览器查看接口；自带请求校验 |
| 数据校验 | Pydantic 2.x | 声明式模型，非法请求自动返回 422 |
| 数据库 | SQLite 3 | 零配置单文件，无需安装数据库服务，便于部署 |
| 数据访问 | 原生 `sqlite3` + 参数化 SQL | 表结构简单，手写 SQL 更能体现数据库设计 |
| 数值类型 | `Decimal` | 十进制精确运算，避免浮点误差 |
| 测试 | `unittest`（标准库） | 无需额外依赖 |

**分层架构**：`api/ → service/ → repository/ → core/`，依赖方向严格单向。换数据库只改 `repository/`；加接口只改 `api/`；改计算规则只改 `service/calculator.py`；调配置只改 `core/config.py`。测试也能分层进行——表达式引擎可直接单元测试，无需启动 HTTP 服务。

**异常体系**（`core/exceptions.py`）

```
AppError                        基类，携带 code / message / status_code
├── ExpressionError             HTTP 400 表达式非法
│   ├── DivisionByZeroError     HTTP 400 除数为零
│   ├── ExpressionTooLongError  HTTP 400 表达式过长
│   └── ResultOverflowError     HTTP 400 结果溢出
├── RecordNotFoundError         HTTP 404 记录不存在
└── DatabaseError               HTTP 500 数据库错误
```

业务层只抛领域异常，不抛 `HTTPException`——这样业务逻辑不依赖 Web 框架，将来若要换成 CLI 或 gRPC 接口，业务层代码无需改动。

### 4.7 计算模块设计（核心）

**为什么不能用 eval**：作业明确禁止。`eval("__import__('os').system('whoami')")` 会让攻击者的命令被执行。因此必须自己实现解析，采用**词法分析 + 递归下降语法分析**两步走。

```
原始字符串 "1+2*3"
  ① normalize_expression()  全角转半角、去空白
  ② validate_expression()   非空 / 长度上限 / 字符白名单
  ③ tokenize()              切成 Token 序列
  ④ Parser.parse()          递归下降 + 求值 → Decimal("7")
  ⑤ format_decimal()        去尾随零、避免科学计数法 → "7"
```

**文法设计（优先级如何体现）**

```
expression := term (('+' | '-') term)*       ← 加减，优先级最低
term       := unary (('*' | '/') unary)*     ← 乘除，优先级更高
unary      := ('+' | '-') unary | primary    ← 一元正负号
primary    := NUMBER | '(' expression ')'    ← 数字与括号
```

**关键点**：优先级不是靠"权重表"比较出来的，而是**由文法层次天然编码**——越靠下的规则结合越紧，所以 `1+2*3` 得到 `7` 而非 `9`。一元正负号单独成层，使 `3*-2`、`--5` 合法。（具体代码与逐条理由见 5.3）

**为什么用 Decimal 而非 float**

```python
>>> 0.1 + 0.2
0.30000000000000004          # float：二进制浮点无法精确表示 0.1
>>> Decimal("0.1") + Decimal("0.2")
Decimal('0.3')               # Decimal：十进制运算，结果精确
```

计算器出现 `0.30000000000000004` 会严重影响体验，因此全程使用 `Decimal`，并设置 28 位有效数字的运算上下文。

### 4.8 计算历史模块设计

**保存流程**：计算成功后自动落库，**失败的表达式不落库**（作业要求历史含"表达式、结果、时间"三要素，失败的计算没有有效结果，记进去只会污染列表）。

```
接收表达式 → validate_expression() ──失败──→ 抛 ExpressionError(400)，不落库
          → Parser.parse()        ──失败──→ 抛 DivisionByZeroError 等，不落库
          → format_decimal() 得到结果
          → INSERT INTO calculation_history
          → 返回结果 + 新记录（含自增 id）
```

**查询流程**：`repository._build_filters()` 动态拼接 WHERE 子句与参数列表 → `SELECT ... ORDER BY id DESC LIMIT ? OFFSET ?` → 配合 `COUNT(*)` 得到总数与总页数。`ORDER BY id DESC` 保证最新计算排在最前。

**删除流程**：前端点击垃圾桶图标 → `DELETE /api/history/{id}` → 后端先用 `record_exists()` 检查，不存在则返回 404 → `DELETE FROM calculation_history WHERE id = ?` → 返回 `200 {"deleted_id": id}`。

**关键设计**：删除后前端**不是**本地移除 DOM 节点，而是**重新查询后端**。这样界面显示的永远是数据库的真实状态，不会出现「前端删了但数据库还在」的不一致。（涉及的具体 SQL 与参数化写法见 5.5）

### 5.1 前端：API 请求封装（超时控制 + 错误归一化）

```javascript
function request(path, options) {
  var settings = options || {};
  var url = config.apiBaseUrl + path;
  var controller = new AbortController();
  var timer = setTimeout(function () { controller.abort(); }, config.requestTimeoutMs);

  var init = {
    method: settings.method || 'GET',
    headers: { Accept: 'application/json' },
    signal: controller.signal
  };
  if (settings.body !== undefined) {
    init.headers['Content-Type'] = 'application/json';
    init.body = JSON.stringify(settings.body);
  }

  return fetch(url, init)
    .then(function (response) {
      return response.json().then(function (data) {
        if (!response.ok) { throw new ApiError(data.message, data.code, response.status); }
        return data;
      });
    })
    .catch(function (error) {
      if (error instanceof ApiError) { throw error; }
      if (error.name === 'AbortError') {
        throw new ApiError('请求超时，请检查后端服务是否已启动', 'TIMEOUT', 0);
      }
      throw new ApiError('无法连接后端服务（' + config.apiBaseUrl + '）', 'NETWORK_ERROR', 0);
    })
    .finally(function () { clearTimeout(timer); });
}
```

### 5.3 后端：递归下降解析器（本项目核心）

```python
class Parser:
    """递归下降解析器，一边解析一边求值。"""

    def _parse_expression(self) -> Decimal:
        """expression := term (('+' | '-') term)*   —— 加减，优先级最低"""
        left = self._parse_term()
        while True:
            if self._match(TokenType.PLUS) is not None:
                left = left + self._parse_term()
            elif self._match(TokenType.MINUS) is not None:
                left = left - self._parse_term()
            else:
                return left

    def _parse_term(self) -> Decimal:
        """term := unary (('*' | '/') unary)*       —— 乘除，优先级高于加减"""
        left = self._parse_unary()
        while True:
            if self._match(TokenType.MULTIPLY) is not None:
                left = left * self._parse_unary()
            elif self._match(TokenType.DIVIDE) is not None:
                divisor = self._parse_unary()
                if divisor == 0:
                    raise DivisionByZeroError("除数不能为零")
                left = left / divisor
            else:
                return left

    def _parse_unary(self) -> Decimal:
        """unary := ('+' | '-') unary | primary     —— 一元正负号"""
        if self._match(TokenType.PLUS) is not None:
            return self._parse_unary()
        if self._match(TokenType.MINUS) is not None:
            return -self._parse_unary()
        return self._parse_primary()
```

**设计理由**

| 设计选择 | 理由 |
| --- | --- |
| **优先级靠文法层次，不用权重表** | `_parse_expression` 处理加减、向 `_parse_term` 要操作数；`_parse_term` 处理乘除、向 `_parse_unary` 要操作数。解析 `1+2*3` 时 `term` 把 `2*3` 整体吃掉返回 `6`，于是得到 `7` 而非 `9` |
| **左结合性靠 `while` 循环** | `8-3-2` 先算 `8-3=5` 再算 `5-2=3`，而不是 `8-(3-2)=7` |
| **一元负号单独成层** | `*` 后的操作数交给 `unary`，而它允许以 `-` 开头，故 `3*-2` 合法；且 `unary` 递归调用自身，`--5` 也合法（若直接调 `primary`，遇 `-` 会报错——这是踩坑后的修正，见 6.1） |
| **边解析边求值** | 四则运算不需要复用中间结果，不建语法树可少一次遍历，代码更短 |
| **除零显式拦截** | 在除法前判断 `divisor == 0`，能给出比 `Decimal` 原生异常更友好的中文提示 |
| **Token 携带位置信息** | 词法分析时为每个 Token 记录 `position`，报错可精确到「位置 4 处」而非笼统的"表达式错误" |

### 5.4 后端：输入校验三重防线

```python
def validate_expression(raw: str) -> str:
    """校验并归一化表达式，返回可直接解析的字符串。"""
    if raw is None or not raw.strip():
        raise ExpressionError("表达式不能为空")

    normalized = normalize_expression(raw)          # 全角 × ÷ 括号转半角、去空白
    if not normalized:
        raise ExpressionError("表达式不能为空")

    if len(normalized) > settings.max_expression_length:
        raise ExpressionTooLongError(
            f"表达式过长，最多支持 {settings.max_expression_length} 个字符"
        )

    illegal = set(normalized) - set("0123456789.+-*/()")
    if illegal:
        raise ExpressionError("表达式包含非法字符：" + "、".join(sorted(illegal)))

    return normalized
```

**三道防线**：①**非空检查**拦空提交；②**长度上限 200 字符**拦超长输入造成的资源耗尽；③**字符集白名单**拦一切非数字/运算符字符，包括注入载荷。

第 ③ 道最关键：`set(normalized) - set("0123456789.+-*/()")` 用集合差集求出所有"不该出现的字符"，非空即拒绝。这样 `__import__('os').system('whoami')` 在这一层就被拦下，根本到不了解析器。**归一化在前、校验在后**也是有意的顺序——用户复制的 `×`、`÷`、全角括号会先转成 `*`、`/`、`(`、`)` 再参与白名单校验。

```python
def _build_filters(keyword, favorites_only) -> tuple[str, list[Any]]:
    """构造 WHERE 子句与参数列表（参数化查询，防 SQL 注入）。"""
    clauses, params = [], []
    if keyword:
        clauses.append("(expression LIKE ? OR result LIKE ?)")
        like = f"%{keyword}%"
        params.extend([like, like])
    if favorites_only:
        clauses.append("is_favorite = 1")
    where = f" WHERE {' AND '.join(clauses)}" if clauses else ""
    return where, params
```

**设计理由**

- **参数化查询（`?` 占位符）** 是防 SQL 注入的关键：SQL 结构可以动态拼接，但用户数据必须走占位符，绝不拼进字符串。
- **把"条件"与"参数"分开返回**，从写法上强制实现上一条原则。
- **插入后回查一次**：`lastrowid` 只给主键，回查能拿到 `created_at`、`is_favorite` 等完整字段一并返回前端，省掉一次额外请求。
- **`with` 上下文管理器**保证事务提交/回滚与连接关闭，中途抛异常也能正确回滚。
- **`result` 存 TEXT 而非 REAL**：SQLite 的 REAL 是 8 字节浮点，无法精确保存高精度 `Decimal`；存字符串可保留任意精度，JSON 传输也不会退化为科学计数法。

**其余逻辑以文字说明**

- **结果格式化**：`Decimal` 默认可能输出科学计数法（`Decimal("1E+2")` 转字符串是 `"1E+2"`），需用 `format(value, "f")` 强制定点输出；同时用 `normalize()` 去尾随零（`3.500`→`3.5`），并按精度上限量化，避免 `1/3` 输出 28 位长尾小数。
- **统一异常处理**：业务层只抛领域异常（如 `DivisionByZeroError` 自带 `status_code = 400`），由 `main.py` 的 `@app.exception_handler` 统一翻译成 `{success, code, message, detail}`。好处是错误结构完全一致、前端只需一套处理逻辑，且 500 错误的原始详情只写日志不外泄。
- **删除后重新查询**：前端删除成功后**不是**本地移除 DOM 节点，而是重新调用 `GET /api/history`，这样界面显示的永远是数据库的真实状态，不会出现「前端删了但数据库还在」的不一致。
- **失败的表达式不落库**：历史记录要求含"表达式、结果、时间"三要素，失败的计算没有有效结果，写入只会污染列表，因此校验或计算失败时直接抛异常、不执行 INSERT。

### 5.6 测试：如何证明"数据真的落库了"

```python
def test_data_is_really_in_database(self) -> None:
    """绕过 API，直接查库确认数据确实落盘。"""
    self.calculate("9+9")
    with get_connection() as connection:
        row = connection.execute(
            "SELECT expression, result FROM calculation_history"
        ).fetchone()
    self.assertEqual(row["result"], "18")
```

只断言 API 返回 `{"result":"18"}` 是不够的——若实现只把数据存在内存字典里，API 测试照样通过。这个测试**绕过 API 直接查数据库**，才能真正证明「计算历史持久化到后端数据库」的要求被满足。删除功能同理，直接查库确认行已消失。

**如何证明没有偷偷用 `eval`**：一是**行为测试**投喂 8 种注入载荷（`__import__('os').system('whoami')`、`eval('1+1')`、`9**9**9` 等）确认全部被拒；二是**静态检查**直接读取 `calculator.py` 源码，断言其中不出现 `eval(` / `exec(`。后者比人工 review 可靠，也能防止将来有人"顺手"加回去。

## 六、个人历程与收获

### 6.1 遇到的问题与解决过程

**问题一：一元负号让解析器崩了**

最初打算用调度场算法（Shunting-yard）把中缀表达式转后缀再求值，因为资料都说这是"标准做法"。写到一半测试 `3*-2` 时结果不对——解析器把 `*` 后面的 `-` 当成二元减号，然后去找左操作数，直接报错。

我先想打补丁：转换前扫一遍，遇到"运算符后紧跟负号"就插入 `0`，把 `3*-2` 改写成 `3*(0-2)`。这样确实能跑，但 `--5` 又不行了，`-(-3)` 也处理不了，补丁越打越多。

后来意识到问题出在**文法设计**上而不是实现细节。重新画了一遍文法，把一元正负号单独设为一层（`expression → term → unary → primary`）。改成递归下降后 `3*-2` 自然就对了，`--5` 也顺便支持了。

> **收获**：遇到"补丁越打越多"的情况，应该退回去检查设计而不是继续打补丁。这次才真正理解了"文法层次决定优先级"——之前只是在课本上背过。

**问题二：0.1+0.2 为什么不是 0.3**

界面输入 `0.1+0.2`，后端返回 `0.30000000000000004`。我以为是解析器有 bug，检查了词法分析和求值逻辑都没发现问题。后来写最小脚本单独验证 `print(0.1 + 0.2)` 才意识到这不是我的 bug，而是**二进制浮点的固有特性**——`0.1` 在二进制里是无限循环小数。

解决办法是全程改用 `decimal.Decimal`。另外还发现 `Decimal` 的一个小坑：它的字符串输出默认可能用科学计数法（`Decimal("100")` 输出是 `1E+2`），需要额外用 `format(value, "f")` 处理。

> **收获**：这是课本讲过但只有亲手踩到才会真正记住的知识点。这种"库的默认行为不符合直觉"的坑，文档里往往一笔带过。

**问题三：部署到 Render 后构建失败**

本地跑得好好的，推到 GitHub 让 Render 构建时报错，日志说找不到 `pydantic-core` 的预编译轮子。我一开始以为 `requirements.txt` 版本号写错了，反复调整 pydantic 版本都不行。后来仔细看日志发现平台使用的 Python 版本是 **3.14**，而我本地是 3.12。

查资料后明白：`pydantic-core` 用 Rust 写成，需通过 PyO3 编译成平台相关二进制轮子。Python 3.14 较新，很多包的预编译轮子还没跟上，pip 只能尝试从源码编译，而在 Render 构建环境里编译会失败。解决办法是在环境变量里加 `PYTHON_VERSION=3.12.0` 锁定 3.12。

> **收获**：以前觉得"Python 版本无所谓，3.x 都能跑"。这次才明白**依赖的二进制轮子与特定 Python 版本 ABI 绑定**，部署环境的 Python 版本必须和开发环境对齐。

**问题四：前端一直说"无法连接后端"**

本地联调时前端一直提示连接失败，F12 报错指向 CORS。我一开始想不通：**前后端都在我的电脑上，为什么还跨域？** 后来查资料才明白 CORS 判断的是**源的组合**（协议 + 域名 + 端口），只要三者任一不同就算跨域。我的前端在 `127.0.0.1:5500`，后端在 `127.0.0.1:8000`，**端口不同就是跨域**。

> **收获**：之前只知道"跨域要加 CORS 头"这个结论，这次终于搞清楚了浏览器为什么要做这个限制，以及预检请求（OPTIONS）的触发条件。我还在项目里加了 `scripts/e2e_check.py` 专门测 CORS 预检，确保这条配置将来不会被误删。

**问题五：直接双击 HTML 文件打不开功能**

写完前端后直接双击 `index.html`，页面显示正常但任何网络请求都失败。排查后发现是 `file://` 协议的问题——浏览器在这种协议下出于安全考虑会限制跨域请求（因为 `file://` 的源是 `null`）。解决办法是用 `python -m http.server 5500` 起本地静态服务器。

> **收获**：理解了"静态文件也需要通过 HTTP 服务器访问"的原因，以前以为起服务器只是为了方便，现在知道这是浏览器安全机制决定的。

**问题六：Render 免费实例冷启动**

部署上线后隔一段时间再访问，前端要等很久才出结果，偶尔直接报"请求超时"。一开始我怀疑又是 CORS 问题（报错信息比较模糊），排查一圈才想到可能是冷启动。查看 Render 文档确认：**免费实例在 15 分钟无请求后自动休眠，下次请求需重新启动容器，耗时约 30~50 秒**。而我前端 `requestTimeoutMs` 只设了 15 秒，必然超时。

解决办法：①把超时放宽到 60 秒；②用 UptimeRobot 每 10 分钟 ping 一次 `/api/health` 保持唤醒。

> **收获**：这是很实际的工程问题——**免费资源的限制会直接影响用户体验，而"服务在线"不是理所当然的**。我在博客和 README 里都加了冷启动提示，避免助教验收时误以为项目坏了。

### 6.2 学到的新知识

| 知识点 | 具体理解 |
| --- | --- |
| **前后端分离的本质** | 不是"用两个框架"，而是**职责边界**。判断标准是"把后端停掉，前端还能不能算出结果" |
| **递归下降 vs 调度场** | 递归下降的代码结构直接反映文法结构，更易读、易扩展；调度场更紧凑，但处理一元运算符不够直观 |
| **文法层次即优先级** | 优先级不是查表比较出来的，而是由规则嵌套关系编码的。写对文法，优先级自然正确 |
| **Decimal vs float** | float 是二进制浮点，不能精确表示十进制小数；涉及金额、计算器等场景应该用 Decimal |
| **CORS 的判定规则** | 源 = 协议 + 域名 + 端口，任一不同即为跨域。同机器不同端口也算跨域 |
| **HTTP 状态码语义** | 201 表示"创建了新资源"，400 是客户端请求本身有问题，422 是格式对但语义非法。用对状态码能让接口自解释 |
| **分层架构的实际收益** | 写测试时感受最明显——测表达式引擎不需要启动 HTTP 服务 |
| **测试要测"证据"而不只是"结果"** | 断言 API 返回了某个值，不足以证明数据真的落库了。直接查数据库才是硬证据 |
| **部署环境的 Python 版本很重要** | 二进制依赖的 wheel 与 Python 版本 ABI 绑定，版本不匹配会导致构建失败 |

### 6.3 关于 AI 辅助开发的反思

本次作业中我借助 AI 工具辅助了部分编码工作，这个过程让我对"如何正确使用 AI 写代码"有了具体认识。

**AI 帮上忙的地方**：生成项目骨架和重复性样板代码（如 README 结构、`.gitignore`）；快速给出某个 API 的用法示例，省去翻文档时间；帮我 review 代码，指出一些边界情况没处理（比如 `1.2.3` 这种输入）。

**AI 帮不上、必须我自己想清楚的地方**：

- **文法的设计。** AI 给的调度场算法版本在 `3*-2` 上是错的，我按它的建议改了两版都不对，最后是自己画出文法层次才解决的。这让我意识到：**AI 能写代码，但不能替我做设计决策**。
- **部署环境的排查。** AI 看不到 Render 的构建日志，也不知道我本地是 Python 3.12。是我自己看日志、对比版本才定位到问题。
- **对本项目的取舍。** 比如"要不要用 ORM"，AI 两个方案都能给，但选哪个取决于"这是作业、要让助教看懂 SQL"这个具体语境。

**我最大的体会**：作业原文明确写了"不要用原型工具直接生成完整作业、在未理解或不加修改的情况下提交"。这次我信了——**如果我只是把 AI 生成的代码交上去，我根本答不出"为什么用递归下降而不是调度场算法"这种问题**，而这类问题恰恰是助教最容易问的。

所以我的做法是：AI 生成的部分我逐段读懂并改成自己的写法；测试用例我自己加了很多边界情况（比如 `9**9**9` 这种资源耗尽攻击）；博客里的踩坑经历全部是我真实遇到的。**如果用 AI 代劳而不理解，最直接的后果就是查重和答辩时露馅。**

### 6.4 可能的改进方向

1. **解决云端数据持久化**：目前 Render 免费实例磁盘是临时的，重新部署会清空历史记录。改用云数据库或挂载 Disk 即可，代价是需学习数据库迁移工具。
2. **表达式解析改为生成 AST**：目前"边解析边求值"，若要支持变量、函数定义、化简，需先构建抽象语法树。
3. **支持更多数学能力**：当前不支持负数开方（复数）、幂运算右结合（`2^3^2` 应为 `512`，目前视为左结合）、`%` 取模运算符。
4. **补充前端自动化测试**：后端有 115 个测试用例，前端全靠手工测试。引入 Jest + jsdom 可对 `api.js` 和 `ui.js` 做单元测试。
5. **加 CI/CD**：目前部署是手动的，可配置 GitHub Actions 在 push 时自动跑测试、自动部署。
6. **接口版本化**：目前路径是 `/api/xxx`，将来改接口应改成 `/api/v1/xxx`，避免破坏已有客户端。
